# Интерфейс YDM для агентов — Gap Analysis

*Дата:* 2026-10-31
*Статус:* зафиксировано после перевода десктопа на rclone bisync и нескольких
задач, выполненных агентом на боевой конфигурации.

## Контекст

У YDM два адресата: человек (`ydm`, меню) и CLI-агент (`ydm-sync-*`, `--format
json`). Этот разбор про второго. Проверка: прогоны команд на ошибочных входах,
чтение `main()` инструментов и задача «добавить папку в синк», выполненная
целиком.

## Что работает

- Без `--apply` ничего не меняется; план показывает точную команду rclone.
- Опасные действия отказываются выполняться (`risk`, индекс демона, устаревший
  скан, изменившийся фильтр).
- JSON-конверт `success` / `data` со `schema`; `status` отдаёт `resync_needed`.
- Карантин и ignore живут в политике и переживают перезапись фильтров.
- Блокировка от двойного запуска bisync.

Эту основу менять не нужно. Ниже — то, что мешает на неё опереться.

## Гэпы

Опыты с отказами проводились на временных каталогах с поддельным rclone; боевая
конфигурация и облако не затрагивались.

### G1. Код возврата не отражает результат — критично ✅ закрыт (Phase 1)

`tools/sync_policy.py`, `tools/sync_bisync.py` и `tools/sync_filters.py`
завершаются с кодом 0 при ошибке: `main()` печатает payload и не вызывает
`sys.exit`. В `sync_exclude.py` и `sync_rename.py` вызова `sys.exit` тоже нет, то
есть они устроены так же; на отказе они не запускались. `ydm.py` ведёт себя
правильно (код 1).

| Вызов | Вывод | Код |
|-------|-------|-----|
| `sync_bisync.py resync --apply`, rclone упал с rc=7 | `error` заполнен | 0 |
| `sync_bisync.py run --local-root <нет такого>` | `success: false` | 0 |
| `sync_policy.py add --path <нет в облаке>` | `success: false` | 0 |
| `sync_policy.py quarantine --path <вне синка>` | `success: false` | 0 |
| `sync_policy.py download-apply --apply`, rclone упал с rc=3 | `success: false` | 0 |
| `sync_filters.py remove --path <нет в снапшоте>` | `success: false` | 0 |
| `ydm.py report scan-info --scan-id <нет такого>` | `success: false` | 1 |

Последствия:

- агент или скрипт, проверяющий код возврата, считает провал успехом;
- `ydm-bisync.service` запускает `run --apply`, поэтому systemd не увидит сбой:
  `systemctl is-failed` и `OnFailure=` не работают, а проверка журнала на
  `Failed with result` ничего не доказывает.

Обратная сторона той же проблемы: `ydm.py`, `cloud_delta.py changes`,
`trash_scan.py` и `sync_tree.py` с `--format json` на пустой базе падают
трассировкой Python (`sqlite3.OperationalError: no such table: scans`). Код 1
верный, но JSON на выходе нет.

### G2. Нет актуальной инструкции для агента — критично

- `docs/QUICKSTART_AI.md` не менялся с 2026-07-12: в нём ни разу не упомянуты
  rclone, bisync и карантин.
- В корне нет `CLAUDE.md` / `AGENTS.md`.
- Нигде нет порядка шагов для типовых задач и списка запретов.

Без этого агент собирает порядок действий из `--help` и истории и обходит
интерфейс там, где не знает штатного пути.

### G3. Preflight не видит недоступные файлы — высокий

`inspect_path` оценивает риски политики и имён. Отдаёт ли облако содержимое, он
не проверяет. `add` отвечает `safe_for_bidirectional: true`, а следующий
`resync` падает на файлах, для которых Яндекс возвращает 500.

Цена высокая: фильтр уже изменён, поэтому до успешного resync `run` отказывается
работать, и синк стоит по всем папкам, а не только по новой.

Метаданные у таких файлов целы, поэтому скан их не отличает: нужна проба
содержимого.

### G4. Причина сбоя нельзя прочитать машинно — высокий

При падении resync поле `error` содержит только `returncode=7`. Имена файлов
есть лишь в `stderr` — сплошной строкой с ANSI-кодами, так что агент разбирает
её регулярками. Следующий шаг (карантин этих файлов) очевиден, но не предложен.

### G5. Нет составных операций — высокий

| Задача | Сейчас | Чего нет |
|--------|--------|----------|
| Добавить папку | скан, `add --apply`, resync, остановка таймера вручную | одной операции с предпроверкой |
| Приостановить синк | `systemctl --user stop` мимо YDM | паузы; `install_timer.sh` умеет `install\|render\|status\|remove` |
| Проверить карантин | самодельный цикл | `quarantine --recheck` |
| Вернуть файл из карантина | `--remove`, resync | возврата с проверкой, что файл читается |
| Состояние системы | десяток команд | единой сводки `doctor` |

Отдельно: файл, который есть на другом устройстве, можно получить только мимо
YDM. Сверка с облаком по md5 при этом тоже делается вручную.

### G6. Ручной запуск зависит от окружения — средний

Таймер задаёт окружение сам, ручной запуск — нет:

- без `YDM_RCLONE` выбирается `rclone` из `PATH`; на Ubuntu 24.04 это 1.60, без
  `--resilient --recover`, и вывод об этом не предупреждает;
- с `https_proxy` из сессии resync может подолгу висеть на листингах
  (`docs/LINUX_RCLONE_SETUP.md`), а инструмент этого не замечает.

### G7. Несогласованность CLI — средний

Инвентаризация CLI (проверено запуском `--help` и исходниками):

| Инструмент | Место `--format` | По умолчанию | Конверт JSON |
|------------|------------------|--------------|--------------|
| `ydm.py` | до подкоманды | text | `success` / `data` |
| `cloud_delta.py` | до подкоманды | text | не проверен |
| `trash_scan.py` | до подкоманды | json | не проверен |
| `sync_tree.py` | без подкоманд | json | не проверен |
| `sync_policy.py` | после подкоманды | text | `success` / `data` |
| `sync_rename.py` | после подкоманды | text | `success` / `data` |
| `sync_bisync.py` | после подкоманды | json | `success` / `data` |
| `sync_exclude.py` | после подкоманды | json | не проверен |
| `sync_filters.py` | после подкоманды | json | `success` / `data` |
| `cloud_probe.py` | нет | — | нет |
| `repair_android_names.py` | нет | — | нет |
| `gen_exclude_list.py` | нет | — | нет |

`tools/ydm_menu.py` интерактивный и в таблицу не входит.

- Умолчания расходятся: один и тот же вызов без `--format` даёт текст или JSON в
  зависимости от инструмента. Перепутанный порядок даёт ошибку argparse (код 2).
- `gen_exclude_list.py` не использует argparse: первый аргумент считается
  токеном. `--help` уходит запросом к API и завершается `401` (код 1). Реальный
  токен в таком вызове не участвует, но это единственный инструмент, у которого
  `--help` ходит в сеть. В CI его `--help` не проверяется.
- `add --apply` уже рендерит фильтры (`backend_action: render-filters`), но
  `docs/LINUX_RCLONE_SETUP.md` показывает `render-filters` отдельным шагом.

### G8. `download-apply` не годится для предзагрузки и не учитывает карантин — средний

`sync_policy.py download-plan` / `download-apply` — штатная выборочная загрузка
(`rclone copy --files-from-raw`). Результаты опыта:

| Проверка | Результат |
|----------|-----------|
| Путь в режиме `bidirectional` | Команда его не видит: `eligible: []`, `nothing_to_download: true`, успех. Берутся только пути `download_only` |
| Файл в карантине | Попадает в `eligible` и в манифест: план читает инвентарь и политику карантина не смотрит. `ignore` в коде плана тоже нет |
| Частичный отказ облака | `error: rclone copy failed (rc=3)`, `success: false`, код 0; имена файлов только в `stderr` с ANSI |
| Каталог фильтра недоступен на запись | `Permission denied`: манифест пишется рядом с фильтром. Это случай десктопа, где родитель зеркала принадлежит root; запасной путь в `var/` есть только у резервных копий фильтра |
| Переключение `download_only` → `bidirectional` через `add --apply` | Работает |

По коду: у вызова rclone нет таймаута и обработки прокси, возраст скана не
проверяется.

Вывод: для предзагрузки команда работает только обходным путём: добавить папку
как `download_only`, скачать, переключить на `bidirectional`, сделать resync. На
десктопе этот путь сейчас упирается в запись манифеста. Предпроверка из G3
решает задачу проще: недоступные файлы видны до изменения фильтра, а файлы
скачивает resync.

## Вне рамок

- Интерфейс для человека — отдельный разбор.
- Сами отказы хранилища Яндекса: задача не в том, чтобы их устранить, а в том,
  чтобы они не останавливали синк и были видны заранее.
