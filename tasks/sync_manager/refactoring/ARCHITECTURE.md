# Архитектура: слои и паттерны (без излишеств)

*Дата:* 2026-01-30  
*Принцип:* паттерны и разделение — ради понятности кода, тестируемости и расширяемости, не ради самих паттернов.

---

## 1. Расположение кода

Код приложения выносится в отдельный каталог **`src/`** (src layout — распространённая практика для Python-проектов):

- Исходники живут в `src/ydm/`, тесты — в `tests/`, корень — конфиги, точка входа, документация.
- Запуск: из корня `python ydm.py` (скрипт импортирует из `ydm`) или `python -m ydm` при установке пакета (`pip install -e .`). Для запуска без установки в `ydm.py` добавляется `sys.path.insert(0, "src")` или используется `PYTHONPATH=src`.

Альтернатива — пакет `ydm/` сразу в корне (без `src/`). Рекомендация: **src/ydm/** для явного разделения «код приложения» и «корень проекта».

---

## 2. Слои (зависимости между пакетами)

Неформальное разделение по направлению зависимостей (сверху вниз — от ввода к данным):

| Слой | Содержимое | Зависит от |
|------|------------|------------|
| **Presentation (CLI)** | Парсинг аргументов, вывод в консоль, вызов команд | Application, при необходимости Config |
| **Application / Use cases** | Оркестрация: «получить дифф», «построить дерево sync», «добавить папку в sync» | Domain, Infrastructure |
| **Domain / Logic** | Правила: «path in synced subset», статусы [S]/[P]/[-], построение дерева по снимку, композитный снимок | Только данные (структуры, множества); не от БД напрямую |
| **Infrastructure** | Хранение (SQLite), сканирование (API, ФС), чтение/запись конфигов (файлы) | Стандартная библиотека, минимум своих абстракций |

На практике:

- **Infrastructure:** `storage/` (SQLite), `scan/` (API, LocalScanner), `config/` (ydm_config.json, .env), `sync/config.py` (yandex-disk config.cfg).
- **Domain:** `sync/logic.py` (is_path_synced, статусы по дереву), часть `analysis/` (композитный снимок, правила «какой скан полный»).
- **Application:** `analysis/analyzer.py` (использует storage + sync.logic для диффа и дерева), сценарии sync (tree, add, inspect) — либо в `sync/` как сервисы, либо в `cli/`.
- **Presentation:** `cli/` — только парсинг и вызов сценариев, форматирование вывода.

Правило зависимостей: **CLI не импортирует storage напрямую** для бизнес-логики — только передаёт его в Analyzer/Sync-сервисы. Анализ и sync-логика не парсят аргументы — только получают параметры (scan_id, path, exclude_dirs и т.д.). Так проще тестировать и менять CLI или добавить другой вход (например, API).

## 3. Паттерны (где уместны)

### 3.1. Передача зависимостей (лёгкий DI)

- **Analyzer** получает `storage` в конструкторе (как сейчас). Получает `exclude_dirs` снаружи (из sync.config), а не читает конфиг сам — так одна ответственность и проще подмена в тестах.
- **Команды sync** (tree, add, inspect) получают: storage (или analyzer), reader exclude_dirs, при необходимости writer exclude_dirs. В CLI создаётся конфиг, передаётся в команду. Без контейнера и «сервис-локатора» — просто аргументы функций/конструкторов.

### 3.2. Единая точка входа для набора команд

- Вместо размазанной логики в одном `command_handler` — явные обработчики: `run_init(storage)`, `run_scan(args, storage, ...)`, `run_report(args, storage, analyzer, ...)`, `run_sync(args, ...)`. CLI только парсит и вызывает нужный `run_*`. Это упрощает добавление команд и тестирование сценариев без парсера.

### 3.3. Чистые функции для доменной логики

- **is_path_synced(path, exclude_dirs)** — чистая функция: вход (строка, множество), выход (bool). Без I/O, без глобального состояния. Легко покрыть тестами и переиспользовать в diff и в sync tree.
- **compute_sync_status(path, exclude_dirs, children_statuses)** — то же: по пути, exclude и статусам детей возвращает full/partial/excluded. Вся логика статусов [S]/[P]/[-] в одном месте.

### 3.4. Чтение конфига как интерфейс (опционально)

- Если позже понадобится подменять источник exclude_dirs (не только файл, но и переменные окружения или другой бэкенд), можно ввести маленький интерфейс: например, `ExcludeDirsReader` с методом `get_exclude_dirs() -> Set[str]`. Реализация — чтение config.cfg. Анализ и sync-команды принимают reader, а не конкретный класс. На первом этапе достаточно одной реализации в `sync/config.py` и передачи множества из CLI — абстракцию можно добавить при появлении второго источника.

### 3.5. Чего не вводить

- **Тяжёлый DI-контейнер** — избыточен при текущем размере проекта.
- **Абстрактные репозитории** при одном бэкенде (SQLite) — достаточно одного StorageManager; абстракцию имеет смысл вводить при появлении второго хранилища.
- **Фасады ради фасадов** — фасад только там, где реально скрывает несколько шагов (например, «получить дерево sync» = взять снимок + exclude_dirs + build_tree_with_sync_status).
- **Сложные билдеры/фабрики** — создание Analyzer и Storage в CLI или в одном месте `create_app()` достаточно.

## 4. Где что лежит (сводка)

| Вопрос | Решение |
|--------|--------|
| Где хранятся exclude_dirs? | Чтение/запись — `ydm.sync.config`; доменная логика «path in sync» — `ydm.sync.logic`. |
| Кто строит дерево облака по снимку? | `ydm.analysis` (данные из storage); дерево со статусами [S]/[P]/[-] — `ydm.sync.logic` (использует данные дерева + exclude_dirs). |
| Кто вызывает API Yandex? | Только `ydm.scan` (CloudScanner, YandexClient). Остальные модули с облаком работают через снимки в БД. |
| Где парсятся аргументы? | Только в `ydm.cli`. Обработчики команд получают уже распарсенные значения. |
| Где общая логика диффа (composite, compare)? | `ydm.analysis.analyzer`; фильтрация по sync — через `ydm.sync.logic.is_path_synced`. |

Эта схема даёт «enterprise-likely» структуру и ясные границы без лишнего оверхеда и без паттернов ради паттернов.
