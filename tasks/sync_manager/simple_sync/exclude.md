## Simple Sync: временный дизайн (быстрое решение)

Этот документ фиксирует «переходный» дизайн для управления синхронизацией без полного рефакторинга.  
Цель — дать CLI‑тул, который корректно правит `exclude-dirs` с учётом фактической структуры облака из БД.

### Цели
- Быстрое, ИИ‑дружелюбное управление синхронизацией без интерактива.
- Корректное «включение подпапки при исключённом родителе» на основе снимка облака.
- Минимум дублирования: использовать существующие `StorageManager`/`Analyzer` и композитный снимок.

### Не‑цели
- Полный рефакторинг (см. `tasks/sync_manager/refactoring/`).
- Интерактивные запросы подтверждений.
- Сканирование облака при работе тулом (используется только БД).

---

## Основная идея
Использовать композитный снимок облака (как в `tasks/smart_diff`) и снимок БД, чтобы:
1) определить структуру подпапок для нужного родителя;
2) корректно пересчитать `exclude-dirs` при добавлении/удалении папки в sync.

### Почему нужен композитный снимок
Частичные cloud‑сканы обновляют отдельные ветки. Композит позволяет получить актуальное состояние по всем папкам, объединяя полный скан и свежие частичные.

---

## Источники данных
- **БД**: `monitor.db` (или путь из `--db-path` как в `ydm.py`).
- **Снимок облака**: композит из `Analyzer.build_composite_scan()`.
- **Конфиг Yandex Disk**: `~/.config/yandex-disk/config.cfg`, поле `exclude-dirs`.

---

## CLI (проект)
### Команды
- `sync add --path /video/n8n [--apply] [--format json|text]`
- `sync remove --path /video/n8n [--apply] [--format json|text]`
- `sync list [--format json|text]`

### Где реализуется
- **Переходное решение:** отдельный скрипт в `tools/` (`tools/sync_exclude.py`).
- **Позже:** перенос в `ydm.py` как подкоманда `sync add/remove/list`.

### Общий модуль (для переиспользования)
Общая логика доступа к БД и композитному снимку выносится в
`tools/sync_common.py` и используется в `sync_tree` и `sync_exclude`:
- нормализация пути;
- выбор `scan_id` по композитному снимку;
- получение списка дочерних папок по `parent_path`;
- чтение `exclude-dirs`.

### Поведение
- **dry‑run по умолчанию**, изменение конфига только с `--apply`.
- JSON‑вывод — стабильный, предсказуемый (для ИИ/скриптов).
- `--no-text-header` — убрать метаданные в text‑выводе.
- `--restart-daemon` — перезапуск демона после apply (по умолчанию).
- `--daemon-status` — статус демона после рестарта (по умолчанию).
- `--restart-delay-sec` / `--status-delay-sec` — задержки (по умолчанию 3 сек).
- `--local-scan` — локальный скан после рестарта (по умолчанию).
- `--local-scan-delay-sec` — задержка перед локальным сканом (по умолчанию 3 сек).
- `--local-root` — путь локального диска (по умолчанию `/data/ya_disk`).

## Логика изменения exclude‑dirs
### 1) `sync add --path /A/B` (включить папку в sync)
Сценарии:
- Если `A` в `exclude-dirs`:
  - удалить `A` из `exclude-dirs`;
  - получить дочерние папки `A` из снимка;
  - добавить в `exclude-dirs` все `A/<child>` кроме `A/B`.
- Если `A` не в `exclude-dirs`:
  - удалить `A/B` из `exclude-dirs` (если было).

### 2) `sync remove --path /A/B` (исключить папку)
- Просто добавить `A/B` в `exclude-dirs` (если нет).

---

## Как получить дочерние папки из БД
### Общая логика с `sync tree`
Для `exclude` нужна та же логика, что и для `sync tree`:
- выбор `scan_id` через композитный снимок;
- получение списка дочерних папок по `parent_path`.
Эта логика должна быть общей (функции/модуль), а не запуском одного тулa из другого.

1) Построить композитный снимок:
   - `composite = Analyzer.build_composite_scan()`
   - `base_scan_id = composite["base_scan_id"]`
   - `folder_updates = composite["folder_updates"]` (mapping: `parent_path -> scan_id`)

2) Для заданного пути `/A` выбрать scan_id:
   - найти **самый длинный** ключ `parent_path` из `folder_updates`, который является префиксом `/A`;
   - если найден, использовать его scan_id;
   - иначе использовать `base_scan_id`.

3) Получить дочерние папки:
```sql
SELECT name
FROM files
WHERE scan_id = :scan_id
  AND parent_path = :parent_path
  AND type = 'dir'
ORDER BY name;
```
Примечание по нормализации:
- В таблице `files` у корня `parent_path = ""`.
- Для `/A` в БД обычно хранится `parent_path = "/A"` (без хвостового `/`).

## Парсинг/запись exclude‑dirs
### Риски
- Запятые в именах папок разрывают `exclude-dirs`.
- Квадратные скобки `[ ]` и слишком длинные имена тоже опасны (см. `TASK_SYNC_MANAGER.md`).

### Нормализация пути
- Вводимые пути нормализуются к виду `/A/B` (с ведущим `/`, без хвостового `/`).
- Для сравнения с `exclude-dirs` используется относительный путь без ведущего `/`.
- Пустое значение трактуется как корень `/` (не используется в `exclude-dirs`).

### Ошибки и формат ответа
- Ошибки возвращаются в JSON с `success=false` и полем `error`.
- Предупреждения не блокируют выполнение и возвращаются в `warnings`.
- Если нет подходящих cloud‑сканов для композитного снимка — возвращать ошибку.

### Поведение при отсутствии сканов
- Если композитный снимок не строится (нет полного scan) — `error`.
- Если путь не найден в снимке — `error` (с указанием пути).

### Минимальный подход для переходного решения
- Парсить строку как CSV по запятым, но **выводить предупреждения**, если часть пути выглядит «подозрительно».
- При записи сохранять список в том же формате (без попытки «исправить» имена).
- Всегда делать бэкап `config.cfg` перед записью.
