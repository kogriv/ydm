**Как делалось.** Сперва полный `git bundle` всей истории и **пробный прогон
на клоне-копии**: пять файлов исчезают, список отслеживаемых файлов совпадает,
тесты зелёные, повторное сканирование чистое, `.git` ужимается с 4,1 МБ до
1,8 МБ. Только после этого — на настоящем репозитории. `git-filter-repo`
запускался распакованным из wheel, без установки в системный Python.

**Цена оказалась меньше заявленной.** Риск «переписывание ломает ссылки на
хеши в доках» был записан крупно; проверка показала, что на хеш ссылается
ровно **один** документ — сам этот набор, написанный в тот же день.

**Чего переписывание не дало — проверено, а не предположено.** После форс-пуша
старый коммит и сам файл **по-прежнему отдаются обоими серверами** по прямому
SHA:

```bash
$ gh api "repos/kogriv/ydm/contents/junk_list.txt?ref=4858601f" --jq .size
24888
$ git fetch git@gitlab.com:kogriv/ydm.git 4858601f…   # exit 0, файл на месте
```

Пока репозиторий приватный, это никого не касается. Но это значит, что
**блокер не снят, а сдвинулся**: чистая история и чистые ветки — необходимое
условие публикации, но не достаточное. Продолжение — Phase 5.

**Exit:** ни один коммит в публикуемой истории не содержит перечня личных
файлов. Достигнуто **локально и в ветках**; на серверах остаются недостижимые
объекты.

## Phase 5 — Убрать остаточные объекты на серверах

*Заведена 2026-08-24 по результату проверки в Phase 1.* Обязательна до
переключения видимости.

Форс-пуш переставляет ветку, но не удаляет объекты. Они становятся
недостижимыми и живут до сборки мусора, а API отдаёт их по точному SHA.
Старые SHA не секрет: они остаются в клонах, в выводе команд, в истории
событий репозитория.

| ID | Task | Acceptance |
|----|------|------------|
| 5.1 | GitLab: исчерпать самообслуживание | ⬜ **сделано, не помогло** — см. журнал ниже |
| 5.2 | GitLab: запрос в поддержку на принудительную сборку мусора | ⬜ инструменты в UI закончились |
| 5.3 | GitHub: запрос в поддержку | ⬜ своего аналога «удалить блобы» там нет вовсе |
| 5.4 | Проверка обеих сторон **непосредственно перед** переключением видимости | обе команды дают ошибку/404 |

### Журнал попыток на GitLab, 24.08

| Что | Результат |
|---|---|
| `Run housekeeping` | объект на месте. Тогда его ещё держали внутренние ссылки, сборщику нечего было брать |
| `Repository cleanup` с `commit-map` от `filter-repo` | письмо «cleanup succeeded», размер репозитория 1,4 МиБ. Ссылок на старую историю не осталось — `git ls-remote` показывает ровно две (`master`, `HEAD`). Объект **на месте** |
| `Run housekeeping` повторно | объект **на месте** |
| `Remove blobs` по пяти ID + `Run housekeeping` | объект **на месте**. Текущая история не пострадала: вершина `38c91d7` совпадает на обеих сторонах |

**Проверка проверки.** Запрос заведомо несуществующего SHA даёт
`not our ref` — значит тест различает «есть» и «нет», а не всегда успешен.

**Вывод.** Объект недостижим, но физически жив. Это ожидаемое поведение `git`:
у висячих объектов есть период отсрочки (по умолчанию две недели), и он
существует ровно затем, чтобы случайно удалённое можно было вернуть. Кликами в
интерфейсе это больше не ускорить — остаётся время или поддержка.

**Что это значит для публикации.** Ничего не блокирует работу над остальным.
Блокируется ровно один момент — переключение видимости, и проверка перед ним
занимает секунды. Публиковать «а потом дочистим» нельзя: после публикации
старые SHA становятся доступны кому угодно, а они не секрет — остаются в
клонах, в выводе команд, в истории событий репозитория.

**Чего делать нельзя.** Пересоздание репозитория гарантированно убирает
остатки, но уничтожает issue #1 и PR #2, на которые ссылается разбор
инцидента. Форков нет (проверено), так что распространения объектов по чужим
копиям не произошло.

**Exit:** ни один сервер не отдаёт удалённые файлы ни по какому SHA.

## Phase 3 — Обезличивание примеров

> **Поправка 2026-08-24.** Эта фаза была записана как «можно делать после
> публикации». Это неверно: личные имена лежат в истории месяцами, и
> публикация делает их публичными навсегда независимо от того, почищено ли
> рабочее дерево. Чистка после — косметика.
>
> Поэтому решение было принято вместе с Phase 1, а не после неё, и **выполнено
> тем же проходом**:

| ID | Task | Files | Acceptance |
|----|------|-------|------------|
| 3.1 | Имя третьего лица → `Sample`, во всей истории | ✅ `--replace-text` в Phase 1 | ни один коммит его не содержит; 240 тестов зелёные |
| 3.2 | `brtn/Запчасти`, `pro/MuSy`, `video/Матеша`, `latoken` | ✅ решено **оставить** | репозиторий и так под именем автора, а разбор инцидента называет рабочий каталог; прятать структуру своих папок, будучи автором, — работа впустую |
| 3.3 | Не трогать исторические документы | ✅ | разбор инцидента с подменёнными путями перестаёт быть разбором |

Правило, по которому это разошлось: **имя живого человека убираем везде,
включая историю; собственные имена папок оставляем.** Первое — данные о
третьем лице, второе — авторство, которое и так не скрыто.

Побочный эффект, который стоит знать: `--replace-text` не различает код и
текст **о** коде, поэтому подстановка задела и документы этой задачи, где
обсуждалось само имя. Формулировки переписаны так, чтобы не называть его
снова — иначе документ вернул бы в историю ровно то, что из неё вычищали.

**Exit:** в исходниках, тестах и истории нет имени третьего лица; имена папок
автора остаются осознанно.
