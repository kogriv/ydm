```bash

$ git fetch git@gitlab.com:kogriv/ydm.git 4858601f…   # exit 0, файл на месте
```

**Exit:** ни один коммит в публикуемой истории не содержит перечня личных

## Phase 5 — Убрать остаточные объекты на серверах

*Заведена 2026-08-24 по результату проверки в Phase 1.* Обязательна до
переключения видимости.

Форс-пуш переставляет ветку, но не удаляет объекты. Они становятся
недостижимыми и живут до сборки мусора, а API отдаёт их по точному SHA.
Старые SHA не секрет: они остаются в клонах, в выводе команд, в истории
событий репозитория.

событий репозитория. Поэтому 5.3 стоит первой в чек-листе публикации, а не в
списке пожеланий.

### Проба 5.3 — как её выполнять

Команда воспроизводимая, занимает секунды. SHA не секрет (см. выше):

```bash
SHA=4858601fe3a5001a170be634f4781ce9e165ebae
D=$(mktemp -d); git init -q "$D"
for r in git@github.com:kogriv/ydm.git git@gitlab.com:kogriv/ydm.git; do
  echo -n "$r : "
  git -C "$D" fetch -q "$r" "$SHA" 2>/dev/null && echo "ЖИВ" || echo "нет"
done
# контроль — проба должна уметь отвечать «нет»:
git -C "$D" fetch -q git@github.com:kogriv/ydm.git \
  0000000000000000000000000000000000000001 2>&1 | tail -1   # ожидается: not our ref
rm -rf "$D"
```

**Замер 25.08.2026:** `ЖИВ` на обоих; контроль дал `not our ref`.

Это не признак того, что чистка не сработала. Переписывание истории было
**24.08**, отсрочка у висячих объектов — две недели, то есть прошёл один день
из четырнадцати. Раньше **~07.09.2026** проверять нечего.

**Замер 23.09.2026:** `ЖИВ` на обоих; контроль дал `not our ref`.

Прошёл **месяц** вместо ожидавшихся двух недель, и объекты отдаются по точному
SHA на обеих сторонах. Это меняет не факт, а **обоснование ожидания**.

Решение 5.2 гласило: «писать в поддержку сейчас — просить о том, что,
вероятно, произойдёт само». Именно это допущение и не подтвердилось. Две
недели — значение `gc.pruneExpire` у обычного git, а не обещание хостинга:
GitLab и GitHub запускают сборку по собственному расписанию, которое снаружи
не наблюдаемо и к сроку отсрочки не привязано. На GitLab самообслуживание
исчерпано ещё 24.08 (журнал выше), на GitHub его нет вовсе.
*(Оба утверждения опровергнуты 24.09 — см. ниже: на GitLab не нажали вторую
кнопку, а на GitHub объект не висячий вовсе.)*

Поэтому 5.4 из условной задачи стала **живым вопросом**: её условие («если
5.3 показала, что объекты живы») выполнено. Ждать дальше можно — но уже как
осознанный выбор, а не потому, что оно вот-вот соберётся само.

Установка владельца «не торопимся и писем не пишем» **остаётся в силе**;
снять её может только он. Здесь записано, что именно изменилось, чтобы
решение принималось по фактам, а не по устаревшему прогнозу.

**Что не изменилось.** Публикацию это блокирует ровно так же, и проверку
перед переключением видимости надо повторить в тот самый момент — сколько бы
раз она ни отвечала `ЖИВ` до этого.

**24.09: владелец снял установку «писем не пишем»** и поручил пройти путь до
конца — с правом отправить письмо, если понадобится.

**Замер 24.09.2026, после `Prune` на GitLab:** GitLab — `not our ref`, GitHub
— `ЖИВ`.

### Почему на GitHub ждать было бесполезно — и было бы бесполезно всегда

На GitHub старый корень **не висячий**. Его держит `refs/pull/2/head` —
закрытый PR #2 от 15.08 («Add Yandex Disk trash restore tooling»), созданный
до переписывания истории. `git ls-remote` показывает ссылки `refs/pull/*`, а
пользователь удалить их не может; проверено для всех PR до 24.08 — старый
корень тянет только #2. Раз объект **достижим**, сборщик мусора его не
тронет ни через две недели, ни через год. Допущение 5.2 для GitHub было
неверным с самого начала, а не устарело.

На GitLab PR-ссылок не было (`master` и `HEAD`), поэтому там хватило кнопки.

`.git/filter-repo/first-changed-commits` (`4858601f…`), отсутствие LFS. Просьба —
разыменовать или удалить PR #2, убрать кэши, собрать мусор.

**Что это значит для публикации.** Ничего не блокирует работу над остальным.
Блокируется ровно один момент — переключение видимости, и проверка перед ним
занимает секунды. Публиковать «а потом дочистим» нельзя: после публикации
старые SHA становятся доступны кому угодно, а они не секрет — остаются в
клонах, в выводе команд, в истории событий репозитория.

**Чего делать нельзя.** Пересоздание репозитория гарантированно убирает

инцидента. Форков нет (проверено), так что распространения объектов по чужим
копиям не произошло.

### 2.6 — как это оказалось проще, чем выглядело

Разбор обещал правку в двадцати одном месте: везде, где печатается ошибка,
надо было бы возвращать статус. На деле хватило трёх строк, потому что все
провалы уже проходят через одну функцию:

- `render()` запоминает, что напечатала провал;
- `run()` возвращает наружу то, что раньше выбрасывал, — «команду обработали
  или нет»;
- `__main__` соединяет эти два факта в код возврата.

Обработчики трогать не пришлось вовсе. Это заодно объясняет, почему дефект
прожил так долго: `return True` в них означает «я это обработал», а не «всё
хорошо», и читается как второе.

**Нашлось при этом ещё кое-что.** `run()` не возвращал ничего — «обработано
или нет» жило только внутри `command_handler()`. То есть первая версия правки
роняла в единицу вообще всё, включая `init`.

**И один тест проходил по неверной причине.** Проверка «отчёт без `--scan-id`
должен падать» была написана как `report --type scan-info`, а тип отчёта —
позиционный аргумент. Argparse отвергал неизвестный флаг и выходил с кодом 2;
тест зеленел, не проверяя ничего. Обнаружилось при ручной сверке, исправлено,
и в докстринге теста это записано — такой тест зеленел бы и на старом коде.

Мутационная проверка: убрать `sys.exit(...)` — падают три теста из шести.

| 3.2 | `brtn/Запчасти`, `pro/MuSy`, `video/Матеша`, `latoken` | ✅ решено **оставить** | репозиторий и так под именем автора, а разбор инцидента называет рабочий каталог; прятать структуру своих папок, будучи автором, — работа впустую |
| 3.3 | Не трогать исторические документы | ✅ | разбор инцидента с подменёнными путями перестаёт быть разбором |

Правило, по которому это разошлось: **имя живого человека убираем везде,
включая историю; собственные имена папок оставляем.** Первое — данные о
третьем лице, второе — авторство, которое и так не скрыто.

Побочный эффект, который стоит знать: `--replace-text` не различает код и
текст **о** коде, поэтому подстановка задела и документы этой задачи, где
обсуждалось само имя. Формулировки переписаны так, чтобы не называть его
снова — иначе документ вернул бы в историю ровно то, что из неё вычищали.

**Exit:** в исходниках, тестах и истории нет имени третьего лица; имена папок
автора остаются осознанно.
