# Android verification — Design

*Дата:* 2026-08-24
*Статус:* предложение, решение за владельцем
*Разбор:* [`GAP.md`](./GAP.md) · *Работа:* [`BACKLOG.md`](./BACKLOG.md)

Что строить, чтобы закрыть оставшиеся две трети, и — что важнее — чего строить
не надо.

## Главный вывод: эмулятор нужен не для того, для чего его собирались строить

Открытых пунктов два, и планирование показало, что **ни один из них эмулятор
не закрывает хорошо**.

### 2.2 — ограничение имён — решается двумя командами, без всего остального

Гипотеза: `/sdcard` отвергает `|` и `:`, а кодировка rclone подменяет их
полноширинными аналогами и потому проходит. Проверить это можно двумя
командами, и ни python, ни rclone, ни Termux для них не нужны:

```bash
touch "/sdcard/Download/ydm-probe-a|b:c.txt"    # ожидание: ошибка
touch "/sdcard/Download/ydm-probe-a｜b：c.txt"    # ожидание: успех
```

Первая воспроизводит дефект. Вторая проверяет, что лекарство работает: именно
такие имена пишет rclone с `encoding = Colon,Pipe` — это уже показано локально
([`GAP.md#g3`](./GAP.md)).

Если первая падает, а вторая проходит — гипотеза подтверждена, и остаётся
только прописать кодировку в документации.

**Это выполнимо на настоящем телефоне за полминуты** — и настоящий телефон
авторитетнее любого эмулятора. Строить виртуальную машину, чтобы выполнить два
`touch`, несоразмерно.

### Phase 3 — терминал Termux — эмулятор воспроизводит хуже всего

Предмет этой части — как ведёт себя **палец на экране**: свайп листает
scrollback или историю команд, залипает ли скролл после pager, помогает ли
`termux-scroll-fix`. В эмуляторе ввод идёт мышью и клавиатурой. То есть ровно
то, ради чего затевалось, там не воспроизводится.

Эмулятор здесь дорог и слаб одновременно.

---

## Тогда зачем эмулятор вообще

Есть третья цель, о которой в бэклоге не было, и вот её эмулятор закрывает
хорошо:

> **Запускать сам YDM на Android воспроизводимо.** Не «проверить два пункта»,
> а иметь окружение, где прогоняется набор тестов под Termux: python той
> версии, что в Termux, файловая система Android, rclone из репозиториев
> Termux.

Сейчас про это не известно ничего. Проект заявляет поддержку Termux, там есть
`repair_android_names.py`, раздел в README и целая задача `rclone_backend` — и
ни одной автоматической проверки, что оно вообще запускается.

Это осмысленная причина потратить несколько гигабайт и вечер. «Проверить
галочку 2.2» — нет.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| **Waydroid** | Нужны модули ядра `binder`; в системе их нет (`/dev/binder*` отсутствует), потребуется root и правка ядра. Контейнер делит ядро с хостом, поэтому эмуляция `/sdcard` отличается — то есть хуже именно там, где нам нужна точность |
| **Loop-образ vfat** | Приблизительно повторяет ограничения FAT, но `/sdcard` на Android — это FUSE поверх ext4, лишь **имитирующий** правила FAT. Совпадение вероятно, доказательством не является. Плюс нужен `mount`, то есть root |
| **Genymotion / коммерческие** | Лицензия, регистрация, внешний сервис — ради задачи, которая закрывается двумя `touch` |
| **Ничего не делать** | Приемлемо для Phase 3, но тогда это надо записать как «остаётся ручным», а не держать открытым пунктом |

## Устройство стенда

Если строить — то так. Всё без `sudo`: `/dev/kvm` доступен через ACL
(`user:kogriv:rw-`), Java 21 установлена.

### Состав

| Компонент | Что берём | Объём |
|---|---|---|
| `cmdline-tools` | архив с developer.android.com, распаковка в `~/android-sdk` | ~150 МБ |
| `platform-tools` | `sdkmanager "platform-tools"` — нужен `adb` | ~15 МБ |
| `emulator` | `sdkmanager "emulator"` | ~400 МБ |
| Системный образ | `sdkmanager "system-images;android-NN;default;x86_64"` | ~1,5 ГБ |
| Termux | APK с F-Droid, ставится `adb install` | ~100 МБ |
| Внутри Termux | `pkg install python rclone` | ~200 МБ |

Итого около 2,5 ГБ. Свободно 1,2 ТБ.

`default`, а не `google_apis`: Play-сервисы не нужны, образ меньше, и Termux
ставится через `adb install`, а не из маркета.

### Запуск без окна

```bash
emulator -avd ydm-probe -no-window -no-audio -no-boot-anim \
         -gpu swiftshader_indirect
adb wait-for-device
```

### Что мешает автоматизации, и как обходится

| Препятствие | Обход |
|---|---|
| Termux требует разрешение на storage через диалог | `adb shell pm grant com.termux …` / `appops`; на Android 11+ — `MANAGE_EXTERNAL_STORAGE` |
| Android 12+ убивает фоновые процессы Termux | Для коротких команд неважно; при нужде — `adb shell settings put global settings_enable_monitor_phantom_procs false` |
| Первая загрузка образа долгая | Снапшот AVD после настройки, дальше старт с него |

### Какую версию Android брать

Зависит от того, что стоит на реальном устройстве: правила `/sdcard` менялись
(scoped storage в 10, ужесточение в 11). Проверять на 14, когда дефект наблюдался
на 9, — проверять не то. **Это вопрос к владельцу, см. ниже.**

## Чего стенд не сможет

Пишется явно, чтобы «проверено на эмуляторе» не читалось шире, чем есть.

- **Не заменяет устройство в вопросе 2.2.** Эмулятор — не телефон владельца:
  другая версия Android, другая реализация хранилища. Отрицательный результат
  доказателен, положительный лишь обнадёживает (это уже записано в
  [`BACKLOG.md`](./BACKLOG.md) 3.3).
- **Не воспроизводит палец.** Вся Phase 3 про сенсорный ввод.
- **Не проверяет реальную синхронизацию** с облаком — по тем же причинам, по
  которым её не проверяет основной стенд.

## Предлагаемый порядок

1. **Два `touch` на настоящем телефоне.** Закрывает 2.2 авторитетнее любого
   эмулятора. Полминуты.
2. **Решение по Phase 3:** признать ручной и записать причину (эмулятор не
   воспроизводит сенсорный ввод) — либо проверить руками на устройстве.
3. **Эмулятор — отдельной задачей и под свою цель:** прогон набора тестов под
   Termux. Не «закрыть хвосты», а узнать то, чего сейчас не знает никто.

---

## Вопрос, который надо решить до сборки

**Какая версия Android на устройстве, где наблюдался отказ с `|` и `:`?**

От неё зависит выбор системного образа, а без совпадения по версии стенд
проверяет не тот случай.
