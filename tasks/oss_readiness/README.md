# OSS Readiness — roadmap/gap-doc для публикации ydm как открытого проекта

*Дата регистрации:* 12.07.2026
*Статус:* **Открыт** (Этап 0 закрыт — аудит; остальное не начато)
*Приоритет:* обсуждается — этот док фиксирует масштаб работы, не берёт
на себя решение "публиковать ли вообще"

---

## 1. Проблема

Проект технически рабочий, активно используется (см. `tasks/rclone_backend/`),
но никогда не рассматривался с точки зрения "готов ли он к тому, чтобы его
увидел посторонний человек / внешний контрибьютор". Нужен явный gap-анализ
и план закрытия разрывов, прежде чем принимать решение о паблише.

## 2. Что уже готово (аудит от 12.07.2026)

Проверено напрямую (`git log --all -p` по всей истории, grep по трекнутым
файлам):

- [x] `LICENSE` — MIT, копирайт generic (`YDM Contributors`), не персональный.
- [x] Секретов в истории git никогда не было — `.env` не коммитился ни разу,
      токенов/паролей нет ни в одном коммите.
- [x] `.gitignore` закрывает `.env`, `*.db`, `var/`, логи — корректно.
- [x] Личное имя/email нигде не засветились в трекнутых файлах.
- [x] Zero-dependency (только stdlib) — не тянет чужой supply-chain риск.
- [x] Документация по объёму уже приличная: `README.md`,
      `docs/ARCHITECTURE.md`, `docs/QUICKSTART_AI.md`, `docs/USAGE_EXAMPLES.md`.

Это значит: **публикация не заблокирована ничем критичным** (не нужно
переписывать историю git, не нужно отзывать токены). Всё ниже — про
качество/зрелость, не про безопасность.

## 3. Бэклог

### Этап 1 — Зачистка личных примеров в текстах

**Не начато.**

- [ ] `DAO`, `pro/mathcoach` и подобные личные имена папок фигурируют как
      примеры путей в `README.md`, `docs/QUICKSTART_AI.md`,
      `docs/USAGE_EXAMPLES.md`, `tasks/rclone_backend/README.md`,
      `tasks/smart_diff*/`, `tasks/sync_manager/`, и в `--help`-тексте
      `tools/sync_filters.py` (`--path Path to include (e.g., /DAO)`).
      Заменить на generic-плейсхолдеры (`/Projects`, `/MyFolder`).
- [ ] Прогнать `git grep` по финальному списку личных маркеров ещё раз
      перед самим паблишем (не полагаться только на этот проход).

### Этап 2 — Курирование документации

**Не начато.**

- [ ] `docs/issues/issues/` (8 файлов) + `issues/done/` + `tasks/*/FIX_PROGRESS.md`,
      `CODE_REVIEW_FINAL.md`, `bad_fin/` и т.п. (~50 файлов суммарно по
      `docs/`+`tasks/`+`issues/`) — читаются как личный дневник отладки,
      не как курируемая документация продукта. Решить: свернуть историю
      в один `CHANGELOG.md`, или вынести дневниковые файлы из
      публикуемого дерева (отдельная ветка/архив), оставив в `tasks/`
      только итоговые README с текущим статусом (как уже сделано в
      `tasks/rclone_backend/README.md`).
- [ ] Проверить, что `docs/PROJECT_YD_MONITOR.md` и `docs/ARCHITECTURE.md`
      не противоречат текущему коду после Этапов 0-7 rclone-backend
      (писались раньше, до backend-абстракции).

### Этап 3 — Стандартная OSS-гигиена

**Не начато.**

- [ ] `CONTRIBUTING.md` — как ставить окружение, как гонять тесты, стиль
      коммитов (уже есть неявный стиль `Этап N: ...` — задокументировать).
- [ ] `CODE_OF_CONDUCT.md`.
- [ ] Issue/PR шаблоны (`.github/ISSUE_TEMPLATE/`, `.github/PULL_REQUEST_TEMPLATE.md`).
- [ ] `SECURITY.md` — как сообщать об уязвимостях (актуально: проект
      работает с токеном доступа к личному Яндекс.Диску).

### Этап 4 — CI

**Не начато.**

- [ ] Сейчас тесты — bash-скрипты (`tests/test_*.sh`), часть из них
      (`tests/test_rclone_backend.sh`) бьёт по живому `yandex:` remote —
      непрогоняемо в CI и внешним контрибьютором без чужих кредов.
      Нужно решить: (а) выделить чисто-логические части (`Analyzer`,
      `StorageManager` на синтетических данных) в юнит-тесты без сети,
      гонять их в CI; (б) integration-тесты пометить как
      manual/local-only, не блокировать PR ими.
- [ ] Skeleton GitHub Actions (`.github/workflows/ci.yml`) — минимум:
      `python -m py_compile` по всем `.py`, юнит-тесты из п. выше.

### Этап 5 — Обобщение rclone-backend/bisync автоматизации

**Не начато.**

- [ ] Самая свежая часть (`tasks/rclone_backend/`, Этапы 0-7) написана
      конкретно под это устройство: пути вроде
      `/sdcard/Download/ya_disk`, `/data/data/com.termux/...`,
      `termux-job-scheduler`. Сам `ydm.py` + API-бэкенд уже общего
      назначения (конфигурируемые пути через `--local-root`/`ydm_config.json`),
      а вот Termux/Android-специфичный слой (wrapper-скрипт,
      job-scheduler регистрация) — нет.
- [ ] Решить: либо явно промаркировать этот слой как "пример для
      Android/Termux, адаптируйте под своё окружение" (дешевле,
      честнее), либо абстрагировать под generic
      "periodic trigger" (cron/systemd timer/JobScheduler — через
      единый интерфейс). Первый вариант выглядит достаточным для OSS —
      не каждый проект обязан работать "из коробки" на любой платформе.

### Этап 6 — Packaging (опционально, зависит от целевого позиционирования)

**Не начато.**

      admin-инструментов), можно пропустить.

### Этап 7 — Локализация (открытый вопрос по объёму)

**Не начато.**

- [ ] README/доки/комментарии сейчас полностью на русском. Решить
      объём: только `README.md` на английский (минимум для discoverability
      на GitHub), билингва, или всё дерево доков. Не блокер для
      публикации как таковой (много успешных OSS-проектов
      не-англоязычные), но сильно влияет на охват аудитории.

## 4. Открытые вопросы (нужно решение пользователя, не техническое)

- Какая целевая аудитория: "открыл исходники для прозрачности"
  (минимум работы — Этапы 1+3 достаточно) или "хочу внешних
  контрибьюторов и звёзды" (нужны все этапы, включая CI и
  локализацию)?
- Публиковать ли `tasks/rclone_backend/` и bisync-автоматизацию как
  есть (с пометкой "написано под конкретное Android/Termux
  окружение"), или сначала обобщать (Этап 5)?
- Объём локализации (Этап 7) — см. выше.
