## 1. Проблема

Проект технически рабочий, активно используется (см. `tasks/rclone_backend/`),
но никогда не рассматривался с точки зрения "готов ли он к тому, чтобы его
увидел посторонний человек / внешний контрибьютор". Нужен явный gap-анализ
и план закрытия разрывов, прежде чем принимать решение о паблише.

качество/зрелость, не про безопасность.

- [x] Пункт (а) закрыт: `tests/test_analyzer.py` (stdlib `unittest`, без
      pytest — без новых зависимостей), 19 тестов, изолированная
      on-disk SQLite фикстура (`StorageManager(use_temp_storage=False)`,
      тот же режим, что уже использует `tools/sync_common.py`), без
      tmpfs и без сети. Покрыты: `get_diff` (simple-режим, exclude-dirs
      фильтрация, валидация scan-ов), `build_composite_scan`
      (folder_updates, nested-конфликты, кэш), `find_last_full_scan`
      (явный scan_id, эвристика по свежести, `reference_full_scan_id`),
      `get_duplicates`/`clean_duplicates`, `get_long_paths`,
      `StorageManager` базовые операции. Подключено в CI
      (`.github/workflows/ci.yml`) отдельным шагом. Проверено, что тесты
      реально ловят регрессии (намеренно сломан один assert → упал,
      возвращён → снова зелёный), не просто "красиво выглядят".
- [x] **Побочные находки при написании тестов** — две реально исправлены
      (13.07.2026, см. `CHANGELOG.md`), две остаются задокументированы,
      но не исправлены:
      - **Исправлено:** `build_composite_scan()`'s "nested folder
        conflict" резолюция на деле была не "уступает более специфичному
        пути, сохраняя родителя" (как предполагает комментарий в коде), а
        **полностью выбрасывала** запись родительской папки из
        `folder_updates`, если была более глубокая — файлы напрямую в
        родительской папке молча оставались на версии из базового скана.
        Убрана резолюция целиком: `_compare_composite_scan` работает по
        точному совпадению `parent_path`, так что "/A" и "/A/B" — это
        независимые ключи без реального конфликта.
      - **Исправлено:** кэш `build_composite_scan()` не срабатывал,
        если на момент вычисления `folder_updates` был пустой (ранний
        `return` до блока записи в кэш) — теперь один путь возврата и
        кэширования для всех исходов, плюс попутно убран
        задублированный (буквально дважды одинаковый) блок записи в кэш.
      - **Не исправлено, вне скоупа:** `get_diff()` читает `exclude_dirs`
        из модульного `DEFAULT_CONFIG["exclude_config"]`, а не из
        `storage.config` — тесты обходят это monkeypatch'ем в `setUp`.
      - **Не исправлено, вне скоупа:** дублирующееся (мёртвое)
        определение `get_connection` в `StorageManager` — второе тихо
        перекрывает первое, PRAGMA-тюнинг из первого никогда не
        применяется.

## 6. Вторая волна — в работе (с 13.07.2026)

Решение: делаем полноценный OSS-проект. Порядок:

1. **Этап 2 (курирование доков) — первым.** До перевода, потому что
   часть дневниковых файлов может быть свёрнута/архивирована — переводить
   их до этого решения было бы потерянной работой.
2. **Расширенная локализация (уточнение Этапа 7)** — после Этапа 2,
   перевести то, что **реально останется** после курирования:
   `docs/ARCHITECTURE.md`, `docs/QUICKSTART_AI.md`, `docs/USAGE_EXAMPLES.md`,
   актуальные (не дневниковые) секции `tasks/*/README.md`. Комментарии в
   коде (`.py`) — **не переводим отдельной кампанией**, слишком дорого и
   рискованно (рассинхрон с кодом); переводятся по ходу, когда файл и так
   правится по другой причине. Исторический Этап-лог в
   `tasks/rclone_backend/README.md` — не переводится (аналог истории
   коммитов, ретроактивно не переводится).
3. **Этап 4 (CI)** — параллельно с 1-2, не зависит от них.
4. **Этап 6 (packaging)** — последним, ниже приоритет.

GitHub-описание репозитория (сейчас пустое) и решение о смене видимости
репо с private на public — вне этого дока, отдельные шаги за
пользователем, уже принято решение подождать с этим до готовности (см.
переписку).
