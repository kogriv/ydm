# `report diff` correctness

*Дата разбора:* 2026-08-16
*Статус:* дефекты 1–3 исправлены; retention (дефект 4) — в бэклоге.

`report diff` — главная функция проекта: сверить облако с локальной копией.
Разбор показал, что она **никогда ничего не сопоставляла**: сравнивались два
множества, которые по построению не могут пересечься.

## Дефект 1 — сравнение по несовместимым путям (критично)

Облачные сканы пишут `parent_path` с ведущим слэшем, локальные — без:

| Сторона | `parent_path` | Корень |
|---|---|---|
| cloud | `/pro/MuSy` | `''` |
| local | `pro/MuSy` | `''` |

Сравнение джойнило их как есть:

```sql
WHERE l.parent_path = c.parent_path AND l.name = c.name
```

Замер на реальной базе (облачный скан 72 × локальный 105):

```text
точных совпадений:                        0
совпадений после снятия ведущего слэша: 9428
```

Следствие: **каждый** файл попадал одновременно в «нет локально» и «нет в
облаке». В последнем прогоне `missing_cloud_count` равнялся ровно числу
файлов в локальном скане — не совпало ничего. Конвенция едина по всей базе
(0 из 856 338 локальных строк с ведущим слэшем), то есть это не регрессия, а
исходное состояние.

Проверяется руками: `/pro/MuSy/actor.hpp` числился отсутствующим локально,
хотя лежит на диске и присутствует в локальном скане.

## Дефект 2 — декартово произведение при сборке композита

```sql
WHERE scan_id IN (<41 скан>) AND parent_path IN (<2249 папок>)
```

Это все пары «скан × папка», а не соответствие «папка → её скан». Любой скан,
у которого есть строки по этой папке, попадал в выборку, и при
`INSERT OR REPLACE` побеждал произвольный, а не самый свежий. Пока композит
нёс 136 заплаток, коллизии были редки; после починки покрытия (2249 заплаток)
это стало систематическим.

## Дефект 3 — три копии одной логики, одна из них мёртвая

Сравнение было продублировано в `_compare_composite_scan()`,
`_compare_simple_scan()` и в хвосте `get_diff()`, причём третья копия
недостижима: все ветви выше неё делают `return`. Ровно та структура, при
которой дефект 1 живёт годами — исправление в одном месте не доходит до
остальных.

## Дефект 4 — исключения проверялись только по первому компоненту пути

```python
root = full_path.strip("/").split("/")[0]
if root in exclude_dirs: continue
```

`exclude-dirs` — не список папок верхнего уровня: на этой машине 45 из 55
записей вложенные (`video/Обучение`, `Books/42`, `pro/vps/Серверы`). Проверка
только первого компонента означала, что сознательно не синхронизируемые файлы
попадали в «нет локально». После починки: 60 880 файлов корректно опознаны как
исключённые из синхронизации.

## Что сделано

Одна реализация вместо трёх:

- `Analyzer._composite_cloud_files()` — собирает облачное множество по
  правилу композита: каждая папка обслуживается своим сканом, без
  перекрёстного произведения.
- `Analyzer._diff_file_sets()` — единственное место, где облако сравнивается
  с локальным, с нормализацией путей на обеих сторонах.
- `normalize_compare_path()` — конвенция сравнения задана явно, а не
  подразумевается.
- `is_path_excluded()` — исключение применяется ко всему поддереву, а не к
  первому компоненту пути.
- Мёртвый хвост `get_diff()` удалён. Блок сравнения ужался с 18 576 до
  5 595 символов.

Результат на реальной базе:

```text
до:    missing_local 17483, missing_cloud 14136, совпадений 0
после: совпадений 14101 из 14136 локальных файлов
       исключено из синхронизации 60880
       нет локально 1, нет в облаке 3
```

Остаток объясним полностью:

- «нет локально» — один файл из мартовской базы, которого нет ни на диске, ни
  в облаке: папку `/brtn/Запчасти` с марта никто не пересканировал. Лечится
  `scan cloud --path /brtn/Запчасти`.
- «нет в облаке» — `RCLONE_TEST` (локальный health-check файл rclone) и два
  текстовых файла, лежащих в корне диска: корень в снимке устарел, о чём
  отдельно предупреждает [`cloud_delta`](../delta_scan/README.md).

Проверка сходимости: `cloud_files_count == matched + excluded + missing_local`
(74 982 = 14 101 + 60 880 + 1) — закреплена тестом.

## Дефект 4 — база не чистится (в бэклоге)

`monitor.db` — 579 МБ, 1 439 569 строк, из них:

```text
cloud-сканы старше базы 72:      458 553  (31%)
local-сканы кроме 3 последних:   809 619  (56%)
```

Январские полные сканы (5, 41, 44, 47, 51) полностью перекрыты базой 72 и не
используются ничем. Команды retention нет — только `report clean-duplicates`
для другой задачи. См. [`BACKLOG.md`](BACKLOG.md).
