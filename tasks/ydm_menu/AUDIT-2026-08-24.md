# YDM Menu — аудит 2026-08-24

*Повод:* вопрос «как через меню запустить умный скан облака». Ответа нет —
никак. Это оказалось не единичной дырой, а следствием того, что меню отстало
от инструментов, поверх которых построено.

*Предыдущий разбор:* [`GAP.md`](./GAP.md) от 8 августа — он о другом моменте, о
том, зачем меню вообще нужно. Этот документ его не заменяет.

*Что проверялось:* 1325 строк в семи файлах `tools/ydm_menu*.py`, состав
пунктов, их соответствие возможностям инструментов, безопасность, покрытие
тестами.

## A. Меню не даёт доступа к половине инструментов

Пунктов девять. Инструментов в `tools/` — четырнадцать. Соответствие такое:

| Пункт меню | Чем закрыт |
|---|---|
| 1 Show sync tree | `sync_tree.py` |
| 2 Add folder from cloud | `sync_policy.py add` + `rclone lsf` |
| 3 Add LOCAL folder to sync | `ydm_menu_orphans.py` |
| 4 Remove folder from sync | `sync_policy.py add --mode disabled` |
| 5 Restart daemon / Run bisync | демон или `sync_bisync.py` |
| 6 Resync baseline | `sync_bisync.py resync` |
| 7 Cloud scan | `ydm.py scan cloud --path` |
| 8 Detailed status | `sync_bisync.py status` + политика |
| 9 Help | — |

Не дотянуто ничем:

| Инструмент | Что делает | Почему это заметно |
|---|---|---|
| **`cloud_delta.py`** | за 1–9 запросов говорит, **что именно протухло** | ядро «умного скана»; меню о нём молчит совсем |
| **`ydm.py report diff`** | сверка облака с локальной копией | это **основная ценность проекта**, и её в меню нет |
| `ydm.py report prune` | чистка базы по явному правилу | база 138 МБ и растёт с каждым сканом |
| `trash_scan.py` | просмотр и восстановление из корзины | инструмент из инцидента 14.08 — когда он нужен, человек в панике, а не в терминале |
| `sync_rename.py` | безопасное переименование через `rclone moveto` | — |
| `repair_android_names.py` | починка имён на Android | вне десктопного сценария, допустимо |

## B. Пункт 7 сканирует, но не знает, что сканировать

Прямой ответ на исходный вопрос.

```python
options = ["/Books/Math", "/DAO", "/pro/agents", "/"]
```

Пункт предлагает выбрать путь из четырёх и запускает `scan cloud --path`. То
есть умеет **выполнить** работу, но не умеет **определить её объём** — а это
ровно то, что делает `cloud_delta.py`:

```
check    1 запрос:  менялось ли на диске хоть что-то
changes  ~9 запросов: какие папки протухли + готовые команды
```

Против ~4600 запросов у полного скана. Человек, работающий через меню, об этом
не узнает никогда: инструмент лежит в `tools/`, меню на него не ссылается,
`grep` по всем семи файлам меню не находит слова `delta`.

Сегодняшняя проверка: `changed: False` — с 23 августа не менялось ничего, и
сканировать не нужно вовсе. Через меню этот факт недоступен.

## C. Захардкоженные пути с одной машины

Три пункта предлагают выбор из списков, вписанных руками:

| Пункт | Список |
|---|---|
| 1 Tree | `/`, `/Books/Math` |
| 2 Add from cloud | `/Books/Math`, `/DAO`, `/pro`, `/video` |
| 7 Cloud scan | `/Books/Math`, `/DAO`, `/pro/agents`, `/` |

Для постороннего они бессмысленны. Хуже: `/Books` на этой машине **отключён**
в политике целиком, а `/Books/Math` предлагается в трёх пунктах из трёх — то
есть список протух даже для владельца.

Это тот же класс, что и алиасы в README: интерфейс описывает конфигурацию,
которой нет.

## D. Меню не показывает свежесть снимка

`snapshot_freshness()` считает возраст базы и долю файлов, которые она
обслуживает. Это видно в шапке `sync_tree` и в `report diff`. **В меню — нет.**

Сейчас на этой машине: база #72, ей 173 дня, покрывает 48% файлов. Человек,
живущий в меню, этого не знает, и все его решения принимаются поверх снимка,
о возрасте которого ему не сказали.

Ирония в том, что предупреждение про устаревший снимок строилось именно для
того, чтобы его увидели. Тест `TestStaleSnapshotSurfaces` называется «шапка —
то место, куда смотрят», и проверяет шапку `sync_tree`, а не меню.

## E. Пункт 8 обещает на демоне то, чего там нет

Шапка это учитывает и делает специально:

```python
# The daemon has no bisync run, lock or resync — do not invent them.
```

А `print_detailed_status()` печатает безусловно:

```
Last run: ...
Lock: ... pid=...
Resync needed: ...
```

На daemon-бэкенде это поля из механизма, которого там не существует. Один и
тот же экран в шапке честен, а в подробностях — нет.

## F. Безопасность: перекос в обе стороны

Удаление сделано хорошо: подтверждение, затем ввод имени папки, затем
отдельный вопрос про локальную копию. Три барьера.

А **добавление** папки применяется сразу, и `ydm-sync-add`/`ydm-sync-rm` идут с
`--apply` без сухого прогона. При этом именно добавление запустило инцидент
14.08 — включение `/Books` привело к удалению 13 893 файлов. Барьеры стоят на
той операции, которая в этом проекте ни разу не навредила.

Смягчает то, что перед добавлением зовётся `action_inspect()` и небезопасный
путь блокируется. Но «показать, что будет сделано, до того как делать» —
отдельная вещь, и её нет.

## G. Чем меню проверяется

12 тестов в `tests/test_ydm_menu.py` плюс 6 на стенде (`TestMenuOnBench`,
`TestMenuHeader`). Покрыты: промпты, конфиг, шапка на обоих бэкендах, сироты,
правка политики, недоступный бэкенд.

Не покрыт ни одним тестом **ни один экран**: `screen_tree`, `screen_add_cloud`,
`screen_remove`, `screen_bisync_run`, `screen_resync`, `screen_cloud_scan`.
Именно там живут захардкоженные пути (C) и там же появится любая новая логика.

Причина известна и записана в `tasks/sync_bench/BACKLOG.md`: у `--non-interactive`
нет машиночитаемого выхода, он лишь отказывается работать:

```python
if args.non_interactive:
    print("Use subcommand, e.g. orphans", file=sys.stderr)
    return 2
```

Экраны читают `stdin` напрямую через `Reader`, и его **можно подменить** —
тесты промптов так и делают. То есть препятствие не техническое: просто никто
не написал.

| 7 | Барьеры не на той операции (F) | требует решения, а не правки |
