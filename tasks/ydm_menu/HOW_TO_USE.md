# YDM Menu — как пользоваться

Интерактивное меню для синхронизации Яндекс.Диска на Termux/Android.
Агенты и скрипты по-прежнему используют `ydm-sync-*` и JSON tools.

## Запуск

```bash
source ~/.bashrc
ydm
# или
ydm-menu
```

Нужен интерактивный терминал (TTY). Для скриптов: `ydm orphans` — JSON со списком локальных «сирот».

## Главное меню

| № | Действие |
|---|----------|
| 1 | Дерево sync — как `ydm-tree`, с выбором пути и глубины |
| 2 | Добавить папку с облака — список подпапок, без ввода кириллицы |
| 3 | **Локальные папки не в sync** — сироты с меткой `[L]` |
| 4 | **Выключить синхронизацию папки** — на демоне; на rclone — убрать из sync |
| 5 | Запустить bisync |
| 6 | Resync baseline (dry-run → подтверждение) |
| 7 | **Сканы и база** — облачные сканы (умный, одна папка, полный), локальный скан, список сканов, уборка базы |
| 8 | Подробный статус (метки по каждому пути политики, размер базы) |
| `d` | **Сверка облака с локальной копией** — то же, что `ydm.py report diff` |
| `t` | **Корзина Яндекс.Диска** — что удалено и точные команды для восстановления |
| 9 | Краткая справка (`h` — синоним) |

`q` или `0` — назад/выход. Enter — значение по умолчанию в подсказках.

Цифры 1–9 стоят там же, где стояли; новое добавляется буквами, чтобы не
ломать привычку. Разбор — [`DESIGN-2026-08-24.md`](./DESIGN-2026-08-24.md).

### Пункт 7 подробнее

Всё про сканы в одном месте. Сверху — состояние, ниже — действия:

```
Cloud snapshot: base #5311, 2026-09-09 03:06:34 (3 d), +25 folder update(s), 74976 files
Local scan:     #5650, 2026-09-13 02:08:01, 917 rows
Database:       53.8 MB, 48 scans, 41 prunable (24.7% of rows)

 1  Check the cloud and refresh what changed   (1 request first)
 2  Scan one cloud folder…
 3  Full cloud scan of the whole disk          (slow)
 4  Rescan the local mirror now
 5  Recent scans…
 6  Clean up the database…
  0  Back
```

**1 — умный путь, и с него стоит начинать.** Один HTTP-запрос: менялось ли на
диске хоть что-нибудь. Если нет — так и говорит, и это законный быстрый ответ.
Если менялось — ищет, какие папки протухли (около девяти запросов против ~4600
у полного скана), и предлагает обновить именно их. Без токена или без сети шаг
пропускается с объяснением, а ручной выбор папки работает.

**3 — полный обход всего диска.** На этом устройстве последний занял около
200 минут, поэтому он спрашивает подтверждение. Нужен редко: только чтобы
обновить **базу** композита. Обычный дрейф закрывается пунктом 1 за минуты,
потому что частичный скан базой стать не может.

**4 — локальный скан.** Обычно происходит сам: перед деревом, внутри
rename-preflight каждые полчаса, после resync. Пункт нужен, когда папку
добавили только что: пока скан её не увидел, она не попадает ни в один
счётчик.

**5 — список сканов.** Десять последних с типом, временем, числом строк и
колонкой `role`. Роль — единственное, чего в самой базе нет: какой скан читает
дерево, решается во время чтения. Смотреть туда стоит до уборки:

```
id      when              type   rows    role
5648    2026-09-13 02:00  cloud  120     folder update
5311    2026-09-09 03:06  cloud  80543   base of the snapshot
```

**6 — уборка базы.** Показывает план и ждёт `y`; база и её обновления не
трогаются никогда. После удаления делает `VACUUM`, иначе файл не уменьшится, а
ради размера всё и затевается.

Строка `Snapshot:` есть и в шапке главного меню — возраст базы и какую долю
файлов она обслуживает. Предупреждение появляется только если устаревшая часть
реально участвует в сравнении.

### Добавление показывает последствия до применения

Пункты **2** и **3** перед тем, как что-то менять, печатают дельту и ждут
одного `y`:

```text
Adding /Books/Math/АнГем as bidirectional will change the daemon config:
  exclude-dirs: 55 -> 97
  no longer excluded (starts syncing):  Books
  newly excluded:                       Books/История, Books/Физика (+41)
Apply? [y/N]
```

Читать надо строку **`no longer excluded`**: это папки, которые до сих пор не
синхронизировались и начнут. Именно так выглядел бы инцидент 14.08 за секунду
до того, как случиться.

Счётчик рядом полезен, но сам по себе ничего не гарантирует — он может
остаться прежним, пока содержимое меняется целиком. Смотрите на имена.

Если применение будет отклонено (папка остаётся в синхронизации, но локально
её нет), предпросмотр скажет об этом сразу — а не после того, как вы нажали
`y`.

### Пункт 4 зависит от бэкенда

У демона нет белого списка: он читает `exclude-dirs` и синхронизирует всё, чего
там нет. Поэтому «убрать из sync» на нём означает **добавить исключение**, а не
удалить запись — удаление записи под чёрным списком, наоборот, **включает**
синхронизацию.

На демоне пункт 4 показывает то, что синхронизируется сейчас:

```text
Folders the daemon is syncing (pick one to STOP syncing):

  1  /brtn
  2  /DAO
  3  /pro
  4  /video
  5  Custom path (a subfolder, e.g. /video/Blender)
  0  Back

Excluded now: 52 folder(s). To start syncing one again use menu 2.
```

Дальше — та же дельта и то же одно `y`, что у пунктов 2 и 3.

Исключение никогда ничего не удаляет: оно только выводит папку из зоны
внимания демона. Обратное действие — включить исключённую папку обратно — живёт
в пункте **2**, где перед применением показывается строка `no longer excluded`.

Локальную копию пункт 4 **не удаляет**. Он печатает готовую команду:

```text
The daemon no longer touches /video. The local copy is untouched;
to reclaim the space:
  rm -rf '/data/ya_disk/video'
```

Порядок «исключить → дождаться перезапуска демона → удалить» — единственный
безопасный, и необратимый шаг сразу за перезапуском демона мы не ставим. Разбор
— [`AUDIT-2026-08-27.md`](./AUDIT-2026-08-27.md).

На rclone пункт 4 работает как раньше: политика там белый список, запись в ней
означает «синхронизируется», и удаление записи выключает синхронизацию.

### Пункт `t` — корзина

Нужен ровно тогда, когда файлы уже пропали. Печатает, что лежит в корзине,
откуда и когда удалено, и **готовые команды** — потому что `trash_scan.py`
просит `--trash-root trash:/Books_<хеш>`, а хеш никто не помнит.
Восстановление остаётся в командной строке: оно меняет данные, и пусть меняет
их явно.

## Типичный сценарий: добавить АнГем в двусторонний sync

1. `ydm` → **3** (локальные сироты).
2. В списке найти `Books/Math/АнГем` по номеру.
3. Режим **1** — bidirectional.
4. Если система предупреждает о рисках — выбрать download-only, cloud scan или force (эксперт).
5. Прочитать дельту и подтвердить.
6. При смене фильтров bisync — ответить **Y** на resync.

Проверка: `ydm-tree` — у папки должна быть метка `[B]`.

## Сценарий: добавить папку, которая есть только в облаке

Так добавляли `/pro/physon` 23.09. Отличие от сценария выше одно: папки нет на
телефоне, поэтому она не «сирота» и пункт **3** её не покажет — нужен пункт
**2**.

1. `ydm` → **2** (добавить папку с облака).
2. Родитель: либо номер из списка, либо последний пункт **Custom path** и путь
   руками (`/pro`) — в списке только шесть верхних папок.
3. В списке подпапок найти нужную по номеру.
4. Режим **1** — bidirectional.
5. Прочитать дельту: `Download filter: 11 -> 12`, `+ pro/physon`. Это и есть
   подтверждение, что добавляется именно то, что нужно.
6. **Y** на resync — без него плановый bisync будет падать, пока фильтр не
   совпадёт с базой.

Проверка: в дереве `[B] physon 100.0%`, и папка появилась на телефоне.

**Если нужной папки в списке подпапок нет**, а в облаке она есть — это не сбой
списка, а устаревший снимок её родителя: папку создали после последнего полного
скана. Обновить список детей родителя, один запрос:

```bash
python3 ydm.py --backend rclone scan cloud --path /pro --depth 1
```

После этого папка появляется и в пункте **2**, и в дереве. Умный скан этого пока
не делает сам — [Phase 18.2](BACKLOG.md).

## Метки в дереве

| Метка | Значение |
|-------|----------|
| `[B]` | Двусторонний sync (bisync) |
| `[B^]` | В sync, но **в облаке ещё ничего** — добавлено и не загружено |
| `[B?]` | В sync, но на диске ничего — зеркальный случай `[B^]` |
| `[B~]` | В sync, на диске часть файлов |
| `[D]` | Только скачивание с облака |
| `[D?]` | То же, но на диске ничего |
| `[L]` | Локально есть, в policy нет — кандидат в меню **3** |
| `[P]` | Родитель с дочерними правилами |
| `[X]` | Отключено в policy |
| `[.]` | Пусто / без особого статуса |

`[B^]` — единственная метка, которую стоит запомнить отдельно: так выглядит
папка между добавлением и первой синхронизацией. Пока она там, единственная
копия ваших файлов лежит на телефоне. Лечится пунктом **6** (resync).

## CLI для агентов (без изменений)

```bash
ydm-sync-add /Books/Math/АнГем
ydm-sync-rm /Books/Math/АнГем      # теперь тоже policy-first
ydm-tree 4
ydm-sync-state
```

JSON: `python3 tools/ydm_menu.py orphans --db-path … --local-root … --policy-path …`

## Если что-то не так

- **Resync «завис» после Y** — обычно это не зависание: rclone работает без вывода.
  Меню теперь показывает **scope** (список папок) и verbose-лог rclone в реальном времени.
  Resync затрагивает **только папки из `.bisync.filters`**, не весь Яндекс.Диск.
  После rclone идёт local scan — может занять ещё 1–2 минуты.
- **Пустое дерево** — сделайте cloud scan (меню **7** или `ydm-scan-cloud /Books/Math`).
- **Новой облачной папки не видно** — обновите список детей её родителя:
  `scan cloud --path <родитель> --depth 1`. Подробнее — в сценарии выше.
- **Нет сирот в меню 3** — проверьте `ydm-tree`: нужна метка `[L]`.
- **Bisync занят** — дождитесь завершения или проверьте lock в меню **8**.
- **Нужен resync** — статус в шапке меню или `ydm-bisync-resync --apply`.
