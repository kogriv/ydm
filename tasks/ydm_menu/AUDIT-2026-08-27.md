## Что показала проверка

```
menu 4 offers 53 entries; first six:
    1  [X] Alena
    2  [X] Books
    3  [X] DS
    ...
entries marked [X] (currently EXCLUDED): 52
entries marked [B]: 0  [D]: 0
```

Пункт называется **«Remove folder from sync»**. Все 52 записи в нём — `[X]`,
то есть **исключённые** папки.

## Механизм

`screen_remove()` перечисляет всё, что есть в файле политики, помечая режим:

```python
for mode_key, marker in (
    ("bidirectional", "[B]"),
    ("download_only", "[D]"),
    ("disabled",      "[X]"),
):
```

и вызывает `action_remove()` → `remove_policy_path()` → удаление записи →
`backend.apply_policy()`.

Под rclone это верно: политика — белый список, запись означает «синхронизируется».
Удалил запись — папка выпала из фильтров. Название честное.

Под демоном политика — **чёрный** список, `exclude-dirs`. Запись означает
«исключено», синхронизируется всё, чего в списке нет. `DaemonBackend`
это и говорит прямым текстом:

```python
"""The daemon only supports bidirectional sync. It uses an exclude-dirs
blacklist: everything not excluded is synced both ways."""
```

Режимы `bidirectional` и `download_only` демон выразить не может вовсе —
`_policy_to_exclude_dirs()` первый игнорирует, на второй бросает
`NotSupportedError`. Поэтому боевая политика состоит из одних `disabled`, и
экран, задуманный как «убрать из синхронизации», целиком превращается в
«добавить в синхронизацию».

## Что видит человек

Вторая строка списка — `Books`. Те самые 113 ГБ из инцидента 14.08.

```
Remove /Books from sync?          → Confirm
Type the name to confirm: Books   → Books
Delete local copy too?            → ...
```

Три вопроса подряд описывают действие, обратное тому, которое произойдёт.
Третий вдобавок бессмыслен: локальной копии нет — папка исключена.

## Насколько это опасно

| | |
|---|---|
| Потеря облачных данных | нет |
| Действие, обратное обещанному | да, на 52 записях из 52 |

Смертельный случай закрыт защитой `deletion_risk_paths`: `Books` локально
отсутствует, значит после снятия исключения демон прочитал бы отсутствие как
удаление, и `apply_policy` отказывается перезапускать демон. Проверено на живой
системе 25.08 — отказ приходит **до** записи конфига.

Но защита срабатывает только когда папки нет локально. **16 из 52** исключённых
папок локально существуют — скелеты внутри `video/`:

```
   72 files  video/Математика
   22 files  video/vim
    1 files  video/Helm
    1 files  video/2023-01-29 гипотезы
    2 files  video/Обучение
    0 files  video/фото
```

Для них никакая защита не сработает, и правильно: удалять нечего, всё на месте.
Пункт «убрать из синхронизации» тихо начнёт тянуть содержимое видеопапки из
облака.

## Почему это не поймал стенд

Политика стенда — rclone-образная, в ней есть все три режима сразу. `[X]` в ней
одна запись из десяти, и список выглядит правдоподобно. **Вырожденный случай —
политика из одних исключений, как на любой машине с демоном, — стендом не
моделируется.**

Существующий тест `test_removing_a_folder_needs_its_name_typed_back` берёт
первую запись, отвечает `y`, потом вводит неверное имя и проверяет, что
политика не изменилась. Он прошёл бы и здесь: он проверяет барьер, а не
направление действия. Гоняется только на `rclone`.

## Решение

Не менять надпись — менять смысл экрана под бэкенд. Прецедент уже есть в
`render_main_menu()`, пункты 5 и 6, с комментарием:

```python
# The daemon syncs continuously and has no resync baseline; naming
# these after rclone bisync misdescribes what they do here.
```

Ровно та же причина, тот же приём:

1. На демоне пункт 4 — **«Stop syncing a folder (exclude)»**: перечисляет то,
   что синхронизируется (облачные и локальные папки верхнего уровня минус
   исключённые), и «убрать» означает **добавить исключение**. Это единственное
   безопасное направление под чёрным списком: исключение никогда ничего не
   удаляет.
2. `[X]`-записи уходят с этого экрана. Начать синхронизировать исключённую
   папку можно пунктом 2 — там есть предпросмотр дельты из 8.7 и коэрсия
   предков, — и экран прямо говорит, куда идти.
3. На rclone пункт 4 остаётся прежним. Единственная правка — `[X]`-запись
   больше не называется «убрать из синхронизации»: под белым списком удаление
   такой записи не меняет синхронизацию вообще, это снятие пометки.

## Чего решение сознательно не делает

**Не удаляет локальную копию.** Освободить место после исключения — законный
сценарий, и порядок для него единственно верный: сперва исключить и дождаться
перезапуска демона, потом удалять. Но ставить необратимое удаление следующим
шагом за перезапуском демона — это класс ошибки, из которого вырос инцидент.
Экран печатает готовую команду (в кавычках, как экран корзины после правки
25.08), а нажимает её человек.
