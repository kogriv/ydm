## Эвристика определения полного скана облака

### 1. Проблема с текущим подходом

Сейчас “полный” cloud-скан определяется по техническому признаку:
- скан считается полным, если в `scan_progress` есть запись `path='/'`.

На практике:
- в реальной БД **нет ни одного** скана с `path='/'` в `scan_progress`;
- при этом есть сканы, которые **логически являются полными**:
  - `status='success'`;
  - `pending=0`, `in_progress=0` (прогресс завершен);
  - большое количество файлов (десятки тысяч);
  - охват по многим корневым папкам (`/Books`, `/Projects`, `/video`, `/pro`, `/distr`, ...).

Пример:
- **Scan 47**:
  - завершен штатно (success, pending=0);
  - ~70K файлов;
  - ходил по множеству корневых папок;
  - логически — **полный скан облака**;
  - но не имеет `path='/'` в `scan_progress` → текущая логика считает его “partial”.

Вывод: **опираться только на `path='/'` нельзя** — это технический артефакт, а не семантика полноты.

---

### 2. Семантика “полного скана”

Нужно разделять:

- **Полный cloud-скан (full cloud scan)**:
  - скан, который **претендует описывать всё облако** на момент времени;
  - стартует логически “от корня” (все корневые папки) и доходит до конца (нет pending).

- **Полный скан поддерева (full subtree scan)**:
  - скан, который полностью прошёл **одну ветку** (`/Projects`, `/distr`, `/Books/...`), но не всё дерево.

Для аналитики (`report diff`, композитный снимок) нужен именно **последний full cloud scan**, а не просто любой успешный скан.

---

### 3. Требования к новой эвристике

1. **Не опираться на `path='/'`** — метка может никогда не ставиться.
2. **Учитывать “свежесть” данных**:
   - в прошлых сканах было ~140K файлов;
   - после чистки облака осталось ~75K;
   - эталон “полноты” должен основываться на **актуальных** данных, а не на старом максимуме.
3. **Быть настраиваемой**:
   - окно свежести по умолчанию: **2 дня**;
   - пользователь должен иметь возможность менять это окно (например, через конфиг).
4. **Давать пользователю контроль**:
   - возможность явно указать эталонный полный скан;
   - возможность увидеть кандидатов и их параметры.

---

### 4. Концепция решения

#### 4.1. Окно свежести

Вводится **окно свежести** для анализа cloud-сканов:

- Параметр конфигурации: `full_scan_fresh_window_days` (по умолчанию **2 дня**).
- В анализ берутся только cloud-сканы, которые:
  - `timestamp >= NOW() - full_scan_fresh_window_days`;
  - или (альтернативно/дополнительно) имеют `id` больше заданного cutoff (последний подтверждённый эталон).

Это позволяет:
- игнорировать старые сканы на 140K файлов, которые отражают уже несуществующее состояние;
- строить “эталон полноты” по **свежему состоянию** облака.

#### 4.2. Эталонный полный скан (reference full scan)

Определяется понятие **reference full scan**:

- Это скан, который считается **эталоном** полного состояния облака.
- Может задаваться:
  - **явно пользователем** (через CLI / конфиг, например `reference_full_scan_id=47`);
  - **автоматически по эвристике** (см. ниже).

Эталон используется:
- как база для композитного снимка;
- как “нормальный” размер и структура для сравнения новых сканов.

#### 4.3. Эвристика полноты скана

Для каждого cloud-скана в окне свежести считаются признаки:

- `files_count` — количество файлов;
- `progress` — нет `pending` / `in_progress`;
- `coverage_top` — охват верхнего уровня:
  - `TOP(scan) = { первый сегмент parent_path }`, например `\"Books\"`, `\"Projects\"`, `\"video\"`, ...;
- `status` — должен быть `success`;
- `recency` — насколько скан свежий (по времени).

На основе этого можно:

1. Найти **максимальный `files_count` в окне свежести**: `max_files_recent`.
2. Рассчитать **нормализованный признак**:
   - `f_files = files_count / max_files_recent` (0..1).
3. Сравнить **охват корневых папок** с эталоном:
   - `coverage = |TOP(scan) ∩ TOP_REF| / |TOP_REF|` (если эталон уже есть);
   - если эталона ещё нет — можно использовать TOP самого большого свежего скана.
4. Ввести пороги:
   - `f_files >= alpha_files` (например, 0.9);
   - `coverage >= alpha_cov` (например, 0.8–0.9);
   - `status='success'`, `pending=0`.

Сканы, удовлетворяющие этим условиям, считаются **кандидатами в полный cloud-скан**.

#### 4.4. Смена эталона после чисток

Ситуация с чисткой:
- Старый эталон имел 140K файлов;
- После чистки появляется новый скан (~75K файлов), который:
  - `success`, `pending=0`;
  - по `TOP` покрывает те же корневые папки;
  - является свежим.

В этом случае:
- Новый скан должен стать **новым reference full scan**, даже если его `files_count` сильно меньше старого.
- Это можно сделать:
  - автоматически (если включён “агрессивный” режим обновления эталона);
  - или через подтверждение пользователя (интерактивно/в логах).

---

### 5. Пользовательский контроль

Пользователь должен иметь возможность:

- **Явно указать эталонный полный скан**, например:
  - `ydm.py report set-full-scan --scan-id 47`;
- **Посмотреть кандидатов**:
  - `ydm.py report full-scan-candidates` — список сканов в окне свежести с их:
    - id, timestamp, files_count;
    - coverage по верхнему уровню;
    - score (оценка полноты).
- **Посмотреть текущий эталон**:
  - `ydm.py report full-scan-info` — показывает текущий reference full scan и его метрики.

Дополнительно:
- В конфиге (`ydm_config.json` или отдельной таблице настроек в БД) хранить:
  - `reference_full_scan_id` (опционально);
  - `full_scan_fresh_window_days` (по умолчанию **2**; может быть изменен пользователем).

---

### 6. Краткий план реализации

1. **Конфигурация** ✅:
   - ✅ Добавлен параметр `full_scan_fresh_window_days` (по умолчанию 2 дня) в `ydm_config.json` и `DEFAULT_CONFIG`.
   - ✅ Добавлена возможность указания `reference_full_scan_id` (опционально) через конфиг.

2. **Сервисный слой (Analyzer / StorageManager)** ✅:
   - ✅ Реализован метод `get_recent_cloud_scans()` для выборки cloud-сканов **в окне свежести**.
   - ✅ Реализовано вычисление метрик:
     - `files_count`;
     - `TOP(scan)` (множество верхнеуровневых папок);
     - `progress` (pending/in_progress) из `scan_progress`.
   - ✅ Реализована эвристика выбора в `find_last_full_scan()`:
     - если `reference_full_scan_id` задан — используется он (с базовой валидацией);
     - иначе выбирается лучший кандидат по свежести и файловому объему в окне свежести.

3. **Интеграция с композитным снимком** ✅:
   - ✅ В `build_composite_scan()` используется **новый reference full scan** через `find_last_full_scan()`:
     - если передан `cloud_scan_id` — базой становится указанный скан (с валидацией);
     - если не передан — выбирается эталон по эвристике (окно свежести, объем файлов, статус).
   - ✅ Реализован fallback:
     - если эвристика не находит подходящего кандидата или возвращает ошибку — используется последний cloud-скан как база (старое поведение).

4. **CLI и диагностика** ✅:
   - ✅ Добавлены подтипы `report`:
     - `full-scan-info` — показывает текущий эталон (результат `find_last_full_scan()`).
     - `full-scan-candidates` — показывает свежие cloud-сканы с метриками (`files_count`, `top_levels`, `f_files`, `score`, `is_best`).
   - ✅ Для отладки можно увидеть, **почему выбран именно этот скан**:
     - `is_best=true` помечает текущий выбранный эталон;
     - метрика `f_files` показывает относительный объем по сравнению с максимумом в окне свежести.
   - ⚠️ Явная команда установки эталона (`set-full-scan`) пока не реализована; эталон можно задать через `reference_full_scan_id` в конфиге.

5. **Документация и тесты:**
   - Описать поведение в `PROJECT_YD_MONITOR.md` и в `TASK_SMART_DIFF.md`.
   - Добавить тестовые сценарии:
     - “старый большой скан + новый меньше, но свежий”;
     - “полный vs один большой частичный (одна ветка)”;
     - проверка влияния `full_scan_fresh_window_days`.

---

### 7. Резюме

- Отказ от привязки к `path='/'` и переход к **эвристической оценке полноты**.
- Использование **окна свежести** (по умолчанию 2 дня, настраиваемое пользователем).
- Введение понятия **reference full scan** с возможностью:
  - автоматического выбора;
  - явного задания пользователем.
- Основа для дальнейшей интеграции с `report diff` и композитным снимком: базовый скан для сравнения будет **действительно последним полным и актуальным** сканом облака.

### Валидация (07.01.2026)

Эвристика протестирована на реальной БД (сканы 47/48/49 — один полный
скан на ~70K файлов + два частичных): все 10 сценариев прошли (загрузка
конфига, окно свежести, выбор кандидата, композитный снимок, явный
`reference_full_scan_id`, настройка окна, fallback при пустом окне,
интеграция с `report diff`, CLI-команды `full-scan-info`/
`full-scan-candidates`). Ключевой результат: корректно выбрала свежий
scan 47 (~70K файлов) вместо устаревшего scan 5 (140K файлов, часть
данных к тому моменту уже была вычищена из облака) — именно тот случай,
для которого эвристика и вводилась.
