## 29.10 07:24 UTC — у телефона ресурсы открыты: своё OAuth-приложение

Причина 410 у телефона — общее OAuth-приложение rclone, а не сеть и не токен:

1. `rclone config reconnect yandex:` с тем же общим приложением — Яндекс вернул тот же
   токен (он ещё был действителен), 410.
2. Отзыв доступа rclone в Яндекс ID (`id.yandex.ru/personal/data-access`), затем
   `reconnect` — новый токен (до 29.10.2027), всё равно 410. Значит, режется
   приложение, а не токен.
3. Своё приложение на `oauth.yandex.ru` («Для авторизации пользователей», веб-сервис,
   Redirect URI `http://127.0.0.1:53682/`, права `cloud_api:disk.info`,
   `cloud_api:disk.read`, `cloud_api:disk.write`). `client_id`/`client_secret` —
   в `.env` проекта (он в `.gitignore`) и в ремоуте `yandex` через
   `rclone config update … --non-interactive`; затем `reconnect` и вход в браузере
   телефона. Результат: `cloud_probe.py check` → `open root=200 files=200`,
   `rclone lsd yandex:/` перечисляет корень.

Резервные копии `rclone.conf`: `.before-reconnect-20261029` (до шага 1) и
`.before-own-app-20261029` (до шага 3), рядом с конфигом.

Тонкость для повторения: `rclone config reconnect` читает ответы из stdin с
буферизацией, `printf 'y\ny\n' |` теряет второй ответ (`Failed to read line: EOF`).
Работает `( echo y; sleep 3; echo y; sleep 900 ) | rclone config reconnect yandex:`
— ввод держится открытым, пока ждут код из браузера.

**Шаг 3 порядка возврата (только чтение, 07:30 UTC):** `rclone check --size-only`


**Потерь нет:** ни в одной папке нет файлов, которые есть локально и пропали в облаке.

**Отказы хранилища подтверждены с телефона.** Файл, на котором ПК стабильно получает

## Проверка 29.10 (позже) — ПК видит 200, телефон по-прежнему 410

Сессия ydm на ПК сообщила, что у неё ресурсный слой **вернулся**:
`/v1/disk/resources?path=/` и `/resources/files` → 200, `cloud_probe.py check` →
`open`. С телефона в тот же час — нет. Замеры телефона (06:02–06:10 UTC):

```
cloud_probe.py check      closed root=410 files=410
rclone lsd yandex:/       [410 - GoneError]
rclone copyto <файл>      [410 - GoneError] на листинге, до скачивания не дошло
/v1/disk                  revision 1793244692176005, used 1 662 430 345 337,
                          trash 112 260 083 254
TLS к mds.storage.yandex.net  проверка чистая (цепочка GlobalSign Root R46)
```

`/v1/disk` у телефона и ПК одинаков (ревизия та же), то есть это один диск; разошёлся
только ресурсный слой. Причина неизвестна: либо токен (на телефоне — из
`rclone.conf`), либо маршрут (у телефона бывает VPN-выход). Аккаунт у ПК и телефона сверен по отпечатку идентификатора (сам отпечаток
в репозиторий не записан: короткий хеш числового id подбирается перебором).

**Токен или сеть: решено, это токен (29.10).**
Первая проверка — `ssh -D` на loopback телефона через `hp` (06:47 UTC, с разрешения
владельца, команд на ПК не запускалось, прокси закрыт): тот же rclone-токен через
сеть ПК — `/v1/disk` 200, корзина 200, `resources?path=/`, `/Books`,
`/resources/files` — 410. Выход при этом прямой выход ПК (домашний), а у сессии ПК первый
замер шёл через Xray на VPS (выход через Xray), так что адрес отличался.

Сессия ПК повторила замер без прокси (`--noproxy '*'`) с того же адреса
прямой выход ПК (домашний): её токен `YANDEX_DISK_TOKEN` (**своё** OAuth-приложение, заведён в
январе) → `resources?path=/` 200, `/resources/files` 200, `/v1/disk` 200; через VPS
тоже 200. Аккаунт тот же (сверено по отпечатку идентификатора). То есть **с одного адреса и
одного аккаунта токен своего приложения получает 200, а токен rclone — 410**. Адрес
не причина.

Что известно о токене телефона: ремоут `yandex` без `client_id` — стандартное общее
приложение rclone; токен выпущен в июле, годен до 10.07.2027, `refresh_token` на
месте, `/v1/disk` его принимает; на ресурсах он работал до 11.10 07:10 UTC. Что именно
режется — приложение rclone целиком или этот токен — не определено. Это не лечится
на стороне проекта.

Что следует отсюда:

- Проба 31413 берёт токен rclone **намеренно**: это тот токен, которым пойдёт синк, и
  пока он получает 410, «closed» — правильный ответ для телефона, даже если для других
  приложений диск давно открыт. Карточка придёт, когда ресурсы откроются именно для
  него.
- Первая версия вывода «авария Яндекса закончилась 29.10» неверна: неизвестно, когда
  своё приложение получило 200 впервые, сессия ПК замерила это лишь 29.10.
- Лечение на стороне владельца (см. «Как лечить» ниже), и вернуть синк можно только
  после него.

**Как лечить (решает владелец; делается один раз, резервная копия `rclone.conf` до
этого):** сначала дешёвый опыт — `rclone config reconnect yandex:` с тем же общим
приложением (если новый токен получит 200 — резалось токен); если и новый 410 — завести
своё OAuth-приложение Яндекса (`client_id` и `client_secret` в ремоуте), затем
`reconnect`. Авторизация идёт в браузере, на телефоне проще через
`rclone authorize "yandex"` на ПК. Права для приложения и порядок — по документации
rclone к Яндекс.Диску (мне это известно по памяти, сверить).

**Со слов сессии ПК, мной не перепроверено** (канал был у неё, не у меня):

- Около 5 % случайных файлов по всему Диску стабильно отдают 500/503 на
  скачивание, на одном и том же файле раз за разом; метаданные и md5 в API видны.
  В `/Books/Deti` и `/Books/0_самоконтроль_концентрация` таких 37 из 181.
- Демон `yandex-disk` 0.1.6.1080 на ПК не принимает сертификат
  `mds.storage.yandex.net` (GlobalSign GCC R46 DV TLS CA 2025, Err 27);
  скачивание через `downloader.disk.yandex.ru` проходит. Системный openssl цепочку
  принимает, у демона зашитое хранилище корней.
- Удалений нет по её данным: 54 записи в корзине, новейшая от 25.10.

**Что это меняет для возврата.** Возвращать синк на телефоне по-прежнему рано, и
теперь по двум причинам: шаг 1 порядка (200 на корне) на телефоне не выполнен, а
даже когда выполнится, «не отдаётся на скачивание» (п. выше) не отличить от
«облако потеряло», если смотреть только листинг. `rclone check --size-only`
сравнивает размеры из листинга API и скачивание не затрагивает, поэтому такие
файлы он не покажет; они проявятся при скачивании в самом bisync. Договорено с
сессией ПК: до выяснения на телефоне не делать resync (меню 6) и
`install_job.sh install`.

`Books/Math/vnesh` добавлена в синк через меню (`3`, принудительно, см. шаг 4
ниже). Resync отложен.

## Что произошло

11 октября 2026 в 10:37 МСК плановый `rclone bisync` на устройстве перестал
проходить и с тех пор падает на каждом прогоне. Причина — на стороне Яндекса:
REST API Диска отвечает `410 GoneError` («Ресурс больше недоступен») на
**любой** запрос к ресурсам живого диска, при том что учётные эндпоинты и
корзина отвечают нормально.

По публичным сообщениям, в ночь на 11 октября остановлен ЦОД Яндекса во
Владимире; это третий ЦОД за четыре дня. Две предыдущие остановки (Сасово
8.10, Калужская область 9.10) на синхронизацию не повлияли — в те сутки
прошло по 48 успешных прогонов из 48. Доступ пропал не одновременно с
остановкой ЦОД, а несколькими часами позже, уже утром.

### Про часовые пояса, прежде чем читать таймлайн

**Все метки в логах ydm — UTC, а не местное время.** proot-контейнер живёт в
UTC (`date +%z` → `+0000`), тогда как Android и Termux на этом устройстве —
`Asia/Krasnoyarsk`, то есть UTC+7 = МСК+4. И `job_run.sh` (`date -Is`), и
`sync_bisync.py` (`datetime.now()`) берут время контейнера. Разница в семь
часов, и она ровно того размера, чтобы сдвинуть событие в другую часть суток
при сверке с внешними событиями.

## Признак в логе

```
INFO  : Path1 checking for diffs
INFO  : Path2 checking for diffs
ERROR : : error listing: [410 - GoneError] Gone (Ресурс больше недоступен.)
NOTICE: Bisync aborted. Please try again.
Transferred:   	          0 B / 0 B, -, 0 B/s, ETA -
```

`rc=1`, не `rc=2`, то есть это не тот случай, когда rclone потерял свои
листинги и требует resync (см. CHANGELOG, 2026-09-13). Локальная сторона
перечисляется нормально; падает облачная.

## Границы отказа (REST API, тот же токен, минуя rclone)

```
200  /v1/disk                     квота, revision
200  /v1/disk/trash/resources     корзина читается
410  /v1/disk/resources?path=/    корень
410  /v1/disk/resources?path=…    любая папка, в том числе с префиксом disk:
410  один конкретный файл по полному пути
410  /v1/disk/resources/download  ссылка на скачивание
410  /v1/disk/resources/files     недавние файлы (на них стоит умный скан)
410  /v1/disk/resources/last-uploaded
410  /v1/disk/resources/public
```

Отсюда: это **не токен** (OAuth принимается, `/v1/disk` отвечает 200), **не
rclone** (прямой HTTP-запрос даёт то же), **не удалённая папка** (корень падает
так же, как лист).

Ловушка для диагностики: `rclone about yandex:` отвечает нормально и показывает
занятое место, потому что ходит в `/v1/disk`. Ремоут выглядит живым, пока не
запросишь список файлов.

Умный скан (`tools/cloud_delta.py changes`) на время аварии тоже нерабочий: его
сметающий проход читает `/resources/files`, то есть попадает в те же 410.
Эндпоинт ревизии при этом доступен, и этим стоит пользоваться — см. ниже.

## Что известно про сохранность данных

Утверждать можно только это:

```
used_space   1 662 008 164 129 B  (1.512 ТиБ)   — та же величина, что 23.09
trash_size   112.3 ГБ
корзина      106 записей, свежайшие от 01.10, обычный латеховский мусор
```

Удаление данных уменьшило бы занятое место или наполнило корзину. Ни того, ни
другого не наблюдается. Это говорит о потере доступа, а не содержимого, но
доказательством не является: `410` буквально значит «ресурс больше недоступен»,
и для сервиса в аварии это скорее режим деградации, чем утверждение о данных.

**Ревизия диска зафиксирована как точка отсчёта**, пока `/v1/disk` отвечает:

```
revision 1791760637536266   (var/cloud_revision.json, 12.10 02:49 UTC)
```

Сама по себе точка отсчёта не говорит, что в облаке не было записей: см. 24.10 —
ревизия похожа на метку времени последнего изменения, и эта уже стояла на
11.10 23:17 UTC, то есть после начала аварии (07:37 UTC). Сдвиг ревизии значит
«что-то менялось», а не «что-то пропало»; что именно, отвечают корзина и
`used_space`, пока ресурсный слой закрыт, и `rclone check` — когда откроется.

## Состояние локального зеркала

11 ГБ, 1017 файлов. Число строк одинаково во всех 21 сохранённых локальных
сканах (1142), удалений в `var/bisync.log` за 19 дней — ноль. Отказ происходит
**до** переноса (`Transferred: 0 B`), то есть авария проявилась в самой
безопасной форме: ошибка, а не пустой список.

Уведомления отработали как задумано: 39 одинаковых сбоев дали одну карточку —
дедупликация по тексту ошибки плюс идентификатор уведомления
(CHANGELOG, 2026-09-13).

## Где здесь риск потерять данные

Не в самом сбое, а в восстановлении. Если облако поднимется с частично
потерянным деревом, двусторонний синк честно повторит потерю локально: файлов в
облаке нет — значит удалить их на диске.

Предохранители:

- `--check-access` — файл-маркер `RCLONE_TEST` должен быть по обе стороны;
- `--max-delete 20` — прогон прерывается, если удалений больше.

От массового случая держат: 1017 локальных файлов против порога 20 — прогон
прервётся. От небольшой настоящей потери не держат: до 20 файлов за прогон,
каждые полчаса, без шума.

Поэтому 12.10 около 02:5x UTC задание 31415 снято с расписания до
проверки облака.
Функциональной потери нет — каждый прогон всё равно падает, — а локальная копия
может оказаться последней.

## Как возвращать синхронизацию

Порядок, а не одна команда:

1. `/v1/disk/resources?path=/` отвечает 200.
2. `python3 tools/cloud_delta.py check --token-source rclone` — сравнить ревизию
   с `1791760637536266`. Изменилась — разобраться, что менялось, прежде чем
   синкать.
3. `rclone check yandex:/<папка> /sdcard/Download/ya_disk/<папка> --size-only`
   по нескольким папкам политики: расхождений быть не должно.
4. Меню → `6` (resync). С 18.10 он обязателен: в синк добавлена
   `Books/Math/vnesh`, фильтры сменились, и `run` до resync откажется
   работать. Это только локальная папка — 14 файлов, 193.5 МБ, в облаке её нет,
   поэтому в шаге 3 её не проверять: расхождение там ожидаемое. Resync файлы и
   выгрузит.
5. Только после этого `bash tools/termux/install_job.sh install`.

Шаг 3 важнее остальных: именно он отличает «облако вернулось» от «облако
вернулось без части файлов».

## Что инцидент выявил в своём хозяйстве

Снятие задания — документированный способ остановить синк — не работало.
`termux-job-scheduler --cancel 31415` отвечает `too many arguments` и ничего не
отменяет: идентификатор передаётся отдельным флагом, `--cancel --job-id 31415`.
`install_job.sh remove` при этом печатал «Cancelled job 31415» независимо от
ответа инструмента. То есть способ остановить синхронизацию молча её не
останавливал, и выяснилось это в тот момент, когда остановить понадобилось.

Отдельно: код возврата этого инструмента не несёт нужного различия — сломанная
форма даёт `rc=1`, а отмена несуществующего задания даёт `rc=0` с текстом
`No job N found`. Поэтому `remove` теперь проверяет не код возврата, а факт:
спрашивает `--pending` и падает, если задание всё ещё числится. Девять тестов,
три мутации сверены (PR #1).
